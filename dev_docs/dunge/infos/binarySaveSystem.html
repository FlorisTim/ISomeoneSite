["title"]Binary save system[/] ["post spckbd"] ["title"]Added in 2026 August[/] I made this system so i can save and load data really fast for my game, It's structured in a way so that i never have to shuffle bytes around, for example, when replacing a value with a value that needs more bytes, then it continues writing at the end of the document, or overwrites bytes that it previously has written to.

The binary save system uses blocks of 24 bytes to store data, one such block can be a reference, or data, for data the first byte is used to display that it is not a reference, then the following 19 bytes are used for data, and the remaining 4 bytes are used to tell the parser where the next block is.

when setting or getting a value, the higher level reader and writer expects a string for the reference, this string then gets hashed, here is the code.

normally this would return a hash that rotates bits, xors, and mutliplies by a number aproximating the golden ratio.

but as you can see this also returns a number if the first character of the input is '%'. this behaviour makes it possible to have some byte files act like arrays and some like actual maps.

The bytes are structured like the following Reference: (flag 1 byte)(data 19 bytes)(next block 4 bytes) Data: (reference 8 bytes)(data size 4 bytes)(first block 4 bytes)(metadata 8 bytes)
24 bytes per chunk makes it quicker to scroll through and find objects.
the 8 bytes of metadata can be used to say what type the contents are, and the first reference block in the document contains how many elements there are.

I also made it parse json into these blocks, it successfully parses all types into bytes, it is expected to clarify what type it is by making everything a string and having the type be in it, for example: { "health": "<**int> 15" }
but you can also use values without clarifying the type, this does make it ambigious because an int could be parsed as a long when it becomes bigger than an int. [/] ["back"]
